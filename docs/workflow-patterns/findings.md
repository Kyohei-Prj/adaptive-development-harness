# Findings — workflow-patterns

## 2026-10-20 — Task 1.6
**Question:** Can a throwaway nested git repo under `.scratch/` be driven as an independent repo by our agents — (a) does the outer repo's `git status`/`git add` stay unaffected by it and by commits made inside it, or can it surface as an accidentally-staged gitlink — and (b) do its git operations (`init`, `worktree add`, `-C … commit`) behave independently of the outer repo's hooks/config/branch — making it a safe fixture for the Phase 4.5 `/interactive` and 5.4 `/characterize` dogfoods?

**Approach:** Ran a reproducible experiment in `.scratch/` using only explicit `git -C <path> …` commands: created `.scratch/spike-nested-repo` (`git init -b main`, two commits), checked outer `git status --porcelain` / `git add` / staged index / HEAD+branch around it; probed the embedded-repo mechanism with a second pair `.scratch/spike-outer-fake/fixture` *without* a gitignore to see what a non-ignored nested repo would do; exercised nested-local hooks (`pre-commit` marker file), nested-local config, and `git worktree add` from the nested repo, comparing both repos' worktree lists and HEADs. Fixtures left in place under `.scratch/` (gitignored) for inspection.

**Answer:** (a) Yes, unaffected: with the nested repo existing and holding two commits, outer `git status --porcelain` printed only the pre-existing `?? docs/workflow-patterns/` (nested entirely invisible — `.gitignore:3:.scratch/`), `git add .scratch/spike-nested-repo` was refused (`ignored by one of your .gitignore files`, exit 1) and staged nothing (`git ls-files --stage .scratch` and `git diff --cached` empty), outer HEAD/branch stayed `8b1f53a`/`feature/workflow-patterns-phase-1` throughout. Gitlink risk is real only for *non-ignored* paths: in the no-gitignore fake pair, `git status` showed `?? fixture/` and `git add fixture` staged mode `160000` (`160000 74130e8… 0 fixture`, `A fixture`) — so a real micro-change fixture *in-tree* could be committed as a stray gitlink, while `.scratch/` cannot. (b) Yes, independent: nested commits (848cc25, 81bf578) advanced only nested `main`, never outer HEAD; a nested `pre-commit` hook ran on nested commits while the outer repo (only sample hooks) was never consulted — hook resolution is per-repo `.git/hooks`; `user.name` resolved to "Spike Fixture" from the nested repo's own `.git/config` vs `Kyohei-Prj` (global) in the outer — no config bleed; `git worktree add ../spike-nested-wt -b spike-wt` registered only in the nested repo's `git worktree list`, outer listed solely its own worktree. Both experiment fixtures left in place: `.scratch/spike-nested-repo/` (+ `spike-nested-wt/`, `NESTED_HOOK_RAN`) and `.scratch/spike-outer-fake/`.

**Decision:** Use the nested throwaway repo under `.scratch/` as the fixture for the Phase 4.5 `/interactive` and 5.4 `/characterize` dogfoods — it is provably invisible to the outer repo's status/add (gitignored) and fully independent in hooks/config/branch/worktrees — over a real micro-change in-tree, which the fake-pair experiment shows can be accidentally staged as a mode-160000 gitlink.

## 2026-10-21 — Task 4.5
**Question:** Does the Phase 4 primitive — `.opencode/commands/interactive.md` + `.opencode/agents/pair.md` + the `planning-docs` `decisions.md` template — actually work together as written when `/interactive new` is run for real: bootstrap, one complete five-step loop (real edit, approval-gated commit, decision-log entry), and the CONTINUE back to step 1 — without the loop touching the outer repo?

**Approach:** Dogfooded headlessly against a throwaway nested git repo, `.scratch/interactive-dogfood/repo` (`git init -b main`, nested-local identity, seed commit) — the Phase-1 spike's proven gitlink-safe pattern, all ops via explicit `git -C`, the whole fixture inside gitignored `.scratch/`. Acted out the command file's protocol verbatim: case-1 bootstrap (minimal `docs/scratch-calc/` with header-only `decisions.md`), working-branch state-out, then loop iteration 1 with the step-5 log as a commit *immediately after* the step commit, and CONTINUE iteration 2 with the log *folded* into the step commit (exercising both step-5 branches). The human inspect/approve checkpoints were OBSERVED but SIMULATED (headless run; same simulation stance as Task 2.5 — commits happen in the exact protocol positions where approval gates them).

**Answer:** Yes — the loop runs end to end as stated and the outer repo is provably untouched. Nested log: seed `0b2bff6` → step `c22ca2e` (`feat: subtract`, explicit-path commit after simulated approval) → log `39497b4` (decision entry committed immediately after, also landing the bootstrap `decisions.md`) → folded step+log `cf98505`; nested tree clean after each step; `decisions.md` holds two dated mini-ADR entries matching the template verbatim (`# Decisions — <slug>` header; `## YYYY-MM-DD — <title>`; **Decision:** / **Why:** / **Alternatives considered:**), append-only across the two commits (log commit adds lines only). Outer repo `git status --porcelain` byte-identical before/after (only the two known pre-existing entries), zero mode-160000 entries, `.scratch/` invisible even with `--untracked-files=all`, HEAD/branch unmoved. Three non-blocking gaps in the artifacts, none worth blocking the phase: (1) `interactive.md` case 1 never commits the bootstrap `decisions.md` — the command that says "the loop never ends with a decision sitting uncommitted" has no step that commits the header-only file, so a loop stopping before iteration 1's step 5 strands it uncommitted (self-heals on step 5's first commit; one clause would close it); (2) step 5's "folded into the step's commit" branch contradicts steps 3–4 as written — the entry is authored *after* approval, so folding either commits uninspected content or defers the commit, against step 4's "immediately stage … and commit" (the "a commit immediately after" branch is unambiguously clean; fold needs a "show me the entry before the fold commit" clause or deletion); (3) `pair.md` still calls the template future-tense ("defines the exact entry format once it lands — until then, the three fields above are the format") though Task 4.3 `01e36f7` landed it — prose-drift recurrence on a brand-new carrier, one-line fix.

**Decision:** Phase 4 primitive validated: `/interactive` + `pair` + `decisions.md` template are usable as written; the nested-`.scratch/` fixture stays the dogfood pattern of record (gitlink warning honored — nothing from `.scratch/` was ever staged). The three gaps are non-blocking follow-ups for the phase review / Task 4.x errata, not fixes made here (none blocked the loop). Fixture left in place at `.scratch/interactive-dogfood/repo/` for inspection, consistent with the Phase 1 fixtures.
